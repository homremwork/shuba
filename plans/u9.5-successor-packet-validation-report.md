# U9.5 successor packet validation stop report

## Status

U9.5 is paused after a successful signed Gradle assembly and before publication of the candidate packet. The generated `1.0.1` APK remains ignored build output and is not accepted release evidence. The accepted `1.0.0` packet below `dist/release` was not modified.

## Observed evidence

1. Candidate source revision `c6ba9e4ad7ac01df82be919c886208340c2c37e2` is clean and records the intended JUCE 9 AGPLv3 route.
2. JUCE resolves exactly to `9.0.1` commit `e18f7f506c0b96f2c738a0bcd7fe6467a5005ad8`.
3. The release contract, generated Android identity, generated inventory, API 34, `arm64-v8a`, and zero-permission gates passed.
4. The PKCS12 alias/private-key password and certificate fingerprint boundary passed without exposing secrets.
5. `:app:assembleRelease_Release` completed successfully and produced one metadata-selected signed `1.0.1` / code `2` APK.
6. Publication then stopped at [`shuba_validate_artifact_directory()`](../tools/release/lib/release-artifact.fish:6) with `artifact output has an unexpected four-file inventory`.
7. The existing directory is itself a coherent historical four-file packet for `1.0.0` / code `1`, with APK SHA-256 `9daf64665835bd5da916e23380a994b8f61c206b981930bfd4d98bdca44deffc` and the same pinned signing-certificate fingerprint. Atomic cleanup preserved it unchanged.

## Root cause

Before staging a successor, [`shuba_release_publish_internal()`](../tools/release/build-android-release.fish:125) validates any existing `dist/release` directory using the **current** contract basename and current-contract APK verifier. This is correct for idempotently replacing an artifact for the same release identity, but it makes every normal version successor impossible: a valid historical packet necessarily has a different basename, version name/code, contract digest, and potentially a different schema/tool descriptor.

Deleting or moving the historical packet manually would bypass the intended pre-replacement safety check. Reinterpreting it under the current contract would falsify historical evidence. Weakening current-candidate verification would be unacceptable.

## Decision options

### Option A — Require an absent final directory

Archive or delete the existing packet outside the workflow, then build the successor.

- Advantage: no tooling change.
- Defect: manual state mutation bypasses the release coordinator, loses atomic rollback to the accepted prior packet, and makes operator behavior part of an undocumented security boundary.
- Recommendation: reject.

### Option B — Accept any four regular files as prior state

Check only directory shape before atomic replacement.

- Advantage: small implementation.
- Defect: permits corrupted, mismatched, unsigned, or probe-contaminated prior state to be treated as rollback-safe.
- Recommendation: reject.

### Option C — Validate the prior packet against its own immutable evidence

Parse the historical packet basename and identity from its provenance, require an exact four-file inventory derived from that basename, verify APK bytes against both checksum and provenance, verify the retained pre/post evidence binds that identity, and independently verify signer/alignment/package/version/SDK/ABI/component/permission/native payload using a narrow historical expectation derived from provenance. Require the same application ID, ABI, and signing certificate as the current successor contract; require the historical version code to be strictly lower; reject probes, malformed/duplicate provenance, unexpected files, symlinks, contract mismatch within the packet, and any failed cryptographic/structural assertion.

- Advantage: preserves historical truth, supports atomic rollback, and keeps current candidate verification unchanged.
- Cost: introduces a focused historical-evidence parser/validator and mutation corpus.
- Recommendation: adopt.

### Option D — Store every packet in a versioned final directory

Publish below identity-derived immutable directories and update a separate current pointer.

- Advantage: durable multi-version retention.
- Cost: changes the final-packet storage/publication model, CI artifact path, upgrade procedure, and cleanup policy; a pointer adds an additional atomicity and symlink-safety boundary.
- Recommendation: defer as a broader release architecture change.

## Recommended controlled correction

1. Keep [`verify-android-apk.fish`](../tools/release/verify-android-apk.fish:1) and current-candidate staging/post-publication checks contract-driven and unchanged.
2. Add a dedicated prior-packet validator in [`release-artifact.fish`](../tools/release/lib/release-artifact.fish:1), not a permissive mode on the public current-candidate verifier.
3. Parse only a strict allowlisted provenance schema. Derive historical basename, APK digest/size, application ID, version name/code, minimum/target SDK, ABI, native library path or schema-approved derivation, and signing certificate. Do not source or evaluate provenance text.
4. Require exactly one historical packet basename and its three sidecars; require all entries to be non-symlink regular files with public-safe modes; reject upgrade/probe names and temporary artifacts.
5. Cross-check APK bytes, checksum sidecar, provenance digest/size, verification evidence markers, signer, alignment, package identity, historical version identity, SDK, denied permissions, component shape, ABI/native inventory, stripped ELF, and launcher resources.
6. Require historical application ID, ABI, and signer to equal the current contract. Require historical version code to be a positive integer less than the successor code. Do not require the historical contract digest to equal the current contract digest.
7. Validate the historical packet before allocating the atomic stage. On any failure, leave the prior packet and generated candidate untouched and stop.
8. Extend black-box mutation coverage for wrong basename, extra/missing file, symlink, checksum/provenance disagreement, malformed/duplicate provenance, wrong signer/application/ABI, non-lower version code, probe contamination, missing pre/post evidence, and a valid `1.0.0` to `1.0.1` successor fixture.
9. Preserve the existing atomic publication tests proving rollback restores the exact prior directory after an injected post-publication failure.
10. Rebuild from the corrected committed source state; do not manually reuse or publish the generated APK from the failed source revision because the release entrypoint hash and immutable source state will change.

## Required specification wording

Amend U9.5 to state that an existing accepted final packet is validated against its own retained immutable evidence before atomic successor replacement. It must never be reinterpreted under the successor contract. Current candidate staging and post-publication verification remain successor-contract-driven. A malformed or unverifiable historical packet is a stop condition, not permission to delete it automatically.

## Non-goals

- No release identity change.
- No manual rename, deletion, move, or publication of the generated `1.0.1` APK.
- No weakening of current APK, signer, permission, component, ABI, stripped-ELF, provenance, or immutable-state checks.
- No versioned-release directory redesign or publication-channel work in this correction.
- No claim that the successful Gradle assembly is an accepted candidate packet.
